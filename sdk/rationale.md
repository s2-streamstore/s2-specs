# SDK Specification Rationale

This document explains why [the SDK specification](spec.md) makes its non-obvious design choices, organized by rule ID. The specification is normative; this file is informative. Recording the reasoning makes it easier for future revisions to evaluate changes with full context. Whenever a revision changes or removes a rule, update its entry here.

All rationales below appeal to the specification's four principles: correctness, elegance, idiom, and efficiency.

## Reading this specification

- **Stable IDs.** Each SDK tags conformance tests with rule IDs. Once Revision 1 is finalized, renumbering rules would silently invalidate those tags across four repositories, so removed rule IDs are retired and never reused. Keeping Revision 1 in draft while the initial SDK implementations shake out edge cases lets the spec tighten cleanly before locking IDs.
- **Canonical names.** Having four SDKs invent four names for the same concept (`inflight` vs. `unacked`; `RangeNotSatisfiableError` vs. `ReadUnwrittenError`) makes documentation, support, and cross-SDK testing harder. Casing and language idioms remain native to each SDK; the [Languages](spec.md#languages) section specifies how this works for error types.
- **Every rule is a requirement.** Mixing caller advice into normative rules obscured what an SDK actually had to implement. Usage advice belongs in each SDK's documentation.

## Terms and error model

- **Connection, attempt.** An HTTP/2 stream is a request, not a TCP connection. Referring to a stream as a "connection" made "a different connection" ambiguous between opening a new HTTP/2 stream and opening a new TCP connection—a distinction T6 depends on. "Connection" refers exclusively to the TCP connection, and "attempt" refers to a single request.
- **Sent.** Whether an attempt sent a batch determines whether its error is definite. Ensuring an attempt sends nothing after it ends (T10) freezes that fact when the error arrives, preventing a late write from turning an already-reported definite error into an indefinite one.
- **Definite.** On a session, a single attempt (HTTP/2 request) may already have acknowledged earlier batches. Evaluating side effects over the entire request would make every late error indefinite, so definiteness is evaluated only against batches that were still unacked when the error arrived. Keeping `ServerError` classification purely a function of `(status, code)` from `error-codes.json`—and `TimeoutError` and `ProtocolError` statically indefinite on side-effecting calls—prevents an ordinarily indefinite error such as `503 unavailable` arriving pre-send on a retry from flipping to definite and being wrapped in `IndefiniteAppendError` when it should remain a plain indefinite error (E5), while T2c still permits retrying an append attempt that sent no unacked batch (or unsent unary request) under `no_side_effects`. Pairing `submit()` with read-only operations reflects A4c's guarantee that a failed or canceled `submit()` accepts nothing, while keeping `AbortedError` indefinite on all other side-effecting calls avoids transport send-race tracking on unary cancellations. Qualifying `GOAWAY` `last_stream_id` to transports that expose that guarantee avoids falsely classifying processed streams as definite in HTTP/2 stacks (such as Rust's `h2`) that also surface a remote `GOAWAY` error on EOF for streams at or below `last_stream_id` without exposing stream IDs.
- **Closing.** Between calling `close()` and the session actually closing, a `submit()` waiting for capacity could otherwise block behind a close it can never outlive. Naming the `closing` state lets A4c fail waiting `submit()` calls immediately and lets A8 define how failures and aborts behave during shutdown.
- **Error model.** The core of the specification is a single chain of concepts: attempt → definite/indefinite → final error → wrapping → batch outcome → session failure. Each is defined in its own section (Terms, E, T, A), so the overview summarizes the flow once with citations to avoid readers having to piece it together—while adding no separate normative text that could drift.

## C. Client

- **C1.** A client that implicitly reads environment variables behaves differently across machines and can silently pick up an unintended token. `from_env()` preserves the convenience while making it explicit. Validating that the access token is non-empty and header-safe at construction avoids panics or late failures when building `Authorization` headers (the same hazard as C4).
- **C2.** An out-of-range setting is a bug in caller code and should fail immediately where configured, rather than surfacing later during an unrelated call. Cross-field constraints like `min_base_delay ≤ max_base_delay` are checked at client construction so builder call order does not matter.
- **C3.** The CLI and all four SDKs read the same endpoint environment variables, so they share one minimal endpoint grammar. Supplying only an account endpoint would silently route basin requests—and the caller's access token—to S2 Cloud, so both endpoints must be provided together. No SDK needed custom endpoint paths, and path joining was a recurring source of bugs (doubled slashes, dropped `/v1` prefixes, routes swallowed into query strings).
- **C4.** The SDK validates only what it needs to construct a well-formed, unambiguous header: empty keys produce an empty `s2-encryption-key` header (which proxies or HTTP stacks may treat like an omitted header), and invalid base64 would otherwise fail late or panic during header encoding. Valid key lengths depend on the stream's cipher, which the SDK does not know, so length validation belongs on the server. Encryption keys are a property of the stream and live on the stream handle, whereas `stream_config` is a create-on-first-use hint passed per call or session (matching all four SDKs).
- **C6.** Advertising only the configured compression algorithm ensures responses use what the caller requested. Because some transports advertise `gzip` automatically when the SDK sets no header (for example, Go's `net/http`), SDKs must always decompress compressed responses and error bodies regardless of the setting. Wire and decompressed frame size limits prevent small compressed payloads from expanding into unbounded memory, while still fitting any valid batch (protobuf encoding can reach roughly twice a batch's metered size: a header with a 1-byte name and 1-byte value is 4 metered bytes but encodes in 8 bytes).
- **C8.** S2 never issues HTTP redirects. Following one could leak the encryption key to a third-party host: Go's `net/http` and `fetch` strip `Authorization` on cross-host redirects, but forward custom headers like `s2-encryption-key`.
- **C9.** When the basin endpoint uses `{basin}.`, the basin name is interpolated into the request hostname; an unvalidated name could redirect requests and credentials to an unintended host. All four SDKs already validated basin names against the server's rule. Other resource names appear only in URL paths, where percent-encoding safely contains them, so client-side validation is not required—though an SDK (such as Rust) may still offer typed, validated wrappers for ergonomic client-side APIs.
- **C10.** Inputs may be re-read on retries or reconnected requests. If caller-owned objects could be mutated in between—as Go's shallow copy of `StreamConfig` previously allowed—a retry could send different parameters than originally requested. Snapshotting inputs when accepted guarantees every attempt sends the same payload.
- **C12.** Giving every client a `close()` method provides a universal way to tear down all client resources—and gives Python and Rust, which lack per-session abort triggers on read sessions, a way to abort them. Keeping a dropped client alive while its sessions remain open prevents sessions from failing simply because the caller dropped a handle. In-flight unary calls fail with `AbortedError` rather than `ClientClosedError` because they may already have taken effect; `ClientClosedError` is reserved for calls made after `close()`, which definitely sent nothing. Closing connections without waiting for the server ensures a stalled server cannot hang `close()`.
- **C13.** Scoping connection pools to the client matches C12 so closing one client never disrupts another. Allowing either a shared pool or separate pools for unary calls and sessions accommodates heterogeneous stacks—such as TypeScript (which uses `fetch` for unary calls and `node:http2` for `s2s` sessions) and Go (which pairs `net/http` with a dedicated HTTP/2 streaming pool)—without forcing them onto a single transport, while letting unified HTTP/2 stacks (Rust, Python) share warm TLS/HTTP/2 connections and T6 retirement signals across unary data-plane calls (`create_stream()`, `check_tail()`) and sessions. All correctness rules hold per pool, and separating unary from streaming adds at most one connection per active basin origin. Evicting only the retiring or failed connection prevents a single draining or broken backend behind a load balancer from tearing down healthy sibling connections to the same origin.
- **C13a.** S2 sessions are long-lived HTTP/2 streams, and S2 Cloud advertises `SETTINGS_MAX_CONCURRENT_STREAMS = 100`. An HTTP/2 client that queues additional streams onto a full connection—such as Go's `StrictMaxConcurrentStreams: true` or a single `hyper` client—stalls new calls behind open sessions until `request_timeout` fires or fails with `REFUSED_STREAM`. Opening additional connections turns stream-limit overflow into a liveness guarantee rather than a silent deadlock. Defaulting to 50 concurrent requests per connection (rather than packing to 100 or splitting at 4) leaves ample headroom below S2's 100-stream limit for stream-close races and bursts, halves drain blast radius and connection-level flow-control contention compared to 100, and keeps TCP/TLS connection counts reasonable for high-fanout workloads without requiring remote `SETTINGS` inspection on transports like `hyper-util`. Clamping to `SETTINGS_MAX_CONCURRENT_STREAMS` when lower handles stricter servers or proxies. Per-connection caps and HTTP/2 flow-control windows remain SDK-specific tuning knobs rather than canonical settings (C5).
- **C13b.** Read sessions have s2s heartbeats every 15 s (T7d), but append sessions and long-waiting unary reads have no application-level keep-alive. Without HTTP/2 `PING` probes, a silently blackholed TCP connection hangs until the OS TCP timeout rather than failing and retrying. Failing timed-out connections through T9 classifies dead-connection failures consistently as `ConnectionLostError` (and closes idle append sessions cleanly per A3) rather than `TimeoutError`. Only active connections need probes, since C13c reaps idle ones—though transports like Go's `x/net/http2` may also probe idle connections until idle timeout.
- **C13c.** Closing connections after 90 s with no active requests (via per-connection timers or a periodic reaper) prevents clients that access many basin origins (`{basin}.b.s2.dev`) from retaining unbounded open sockets and avoids waking up on connections silently dropped by NAT gateways or load balancers. Reaping all idle connections—rather than pinning one warm connection per origin—bounds idle socket count to zero when a client is quiet.

## D. Data

- **D1.** `AppendRecord` and `SequencedRecord` are the names three of the four SDKs already use. Requiring `s2-format: base64` on JSON transports for arbitrary byte payloads ensures non-UTF-8 bodies and headers round-trip identically across JSON and Protobuf transports (C5).
- **D2.** `ignore_command_records` was removed. Client-side filtering obscured stream progress: a unary read containing only command records returned an empty batch, leaving the caller with no sequence number to resume from. Preserving resume position required synthesizing a `next_seq_num` the server does not return, introducing awkward edge cases. Exposing `is_command_record()` makes filtering a one-liner for callers while keeping read positions transparent. Accepting an optional `timestamp` on `fence()` and `trim()` ensures command records work on streams with `client-require` timestamping, and recognizing any single empty-named header stays forward-compatible with future command record types.
- **D4.** Record timestamps are integer milliseconds that callers may supply arbitrarily, so they need not represent wall-clock time. Exposing or accepting a date type implies semantics and conversions the API does not have, and date types cannot represent every `u64` value accurately. By contrast, RFC 3339 fields (`created_at`, `expires_at`) and metrics timestamps (`start`, `end`, datapoint/record timestamps) genuinely represent wall-clock time, so native date types fit them—with optional integer Unix epoch seconds accepted as input in languages with union types (Python, TypeScript). Rejecting RFC 3339 inputs outside years `0000`–`9999` eagerly prevents wider native date types (such as Go `time.Time`, JS `Date`, or Rust `jiff::Timestamp` at its lower bound) from failing late or serializing non-RFC 3339 strings, while allowing narrower native bounds (Python's `datetime.MINYEAR == 1` and `jiff::Timestamp::MAX`, `9999-12-30T22:00:00.999999999Z`) to reject out-of-range values rather than silently clamping them. Flooring sub-second precision on metrics date inputs lets callers pass `now()` naturally without manual truncation and keeps adjacent `[t0, t1)` / `[t1, t2)` query windows non-overlapping; unlike whole-second config durations such as `min_age` (D5), flooring a wall-clock instant does not invert semantics. Unrepresentable server numbers must fail rather than silently round, since a rounded sequence number would read or trim the wrong record. TypeScript stays with `number` because sequence numbers will not reach `2⁵³` in practice, and `bigint` is awkward with standard arithmetic and `JSON.stringify`.
- **D5.** Silently coercing invalid caller numbers causes subtle bugs: a `NaN` timestamp was previously dropped on one transport and aborted the session on another, and a 500 ms `min_age` truncated to `0` silently disabled delete-on-empty. Validating eagerly puts the error next to the bad input.

## E. Errors

- **E1.** Callers who want a single catch-all handler for S2 failures need a common base type. Each SDK previously had one, but not every error inherited from it. Go uses an interface since its concrete error types are distinct structs.
- **E2.** Turning every non-2xx response into a `ServerError` with its HTTP status ensures proxy HTML error pages and empty `502` responses are still classified by status (E4c) rather than becoming non-retryable `ProtocolError`s. `412` and `416` are the server errors callers handle programmatically most often, so they get dedicated types—used only when the body actually contains the typed payload. Names describe the failure condition rather than the HTTP status (`ReadUnwrittenError`, not `RangeNotSatisfiableError`, matching `SeqNumMismatchError` and `FencingTokenMismatchError`). The `412` fields (`current_fencing_token` and `assignable_seq_num`) reflect the stream's actual state, matching the API docs; the previous `expected*` names used in three SDKs read ambiguously as the caller's input.
- **E3.** Keeping HTTP statuses and server error codes exclusively on `ServerError` prevents synthetic SDK statuses (like TypeScript's `499`) or codes (like Go's `VALIDATION`) from being mistaken for server responses. Classifying SDK errors from the failing operation—not message text—avoids brittleness when runtimes reword messages or applications happen to pass matching text. A single `TimeoutError` covers request, ack, and heartbeat timeouts because callers classify and handle all three identically (the message identifies which timer fired). Python's `TimeoutError` also subclasses the built-in `TimeoutError` so standard handlers catch it.
- **E4.** `is_retryable` answers a single question: might the cause be transient? Whether retrying is safe is answered separately by `has_no_side_effects`. Earlier designs conflated the two, marking a wrapped append error non-retryable while marking an unwrapped indefinite `503` retryable, even though both are equally unsafe to repeat. Falling back to HTTP status when a code is missing or paired with an unexpected status handles proxies and load balancers safely. Because `412` responses use a condition payload rather than a standard error code, E4e classifies them as definite directly. The spec uses "definite" as concise prose shorthand for `has_no_side_effects`; renaming the public predicate would create churn across all four SDKs with no gain in clarity.
- **E4a.** Keeping the error-code table as data in `s2-specs` gives all four SDKs (via their submodule) and the documentation site a single source of truth, preventing drift like TypeScript previously knowing only three side-effect-free codes.
- **E5.** A retried append can fail with a definite error on its last attempt even though an earlier attempt may have succeeded. Returning the bare definite error would falsely tell the caller that nothing was appended. The wrapper must not match as its inner error's type, so a caller catching `SeqNumMismatchError` to infer "not appended" is not misled. Setting the inner error as the error's cause works in Python, TypeScript, and Rust because `except`, `instanceof`, and `match` do not follow causes. In Go, `errors.Is` and `errors.As` traverse `Unwrap`, so Go wrappers deliberately omit `Unwrap`. (`AbortedError` is not a wrapper, so its context error remains in Go's `Unwrap` chain.) The type was renamed from `AppendIndefiniteFailureError` to `IndefiniteAppendError` to be shorter and clearer.
- **E6.** Giving closed-session rejections their own type lets callers distinguish "this call was rejected because the session closed" from the underlying error that closed the session (accessible via `failure`).
- **E7.** Including the attempt count in the error message signals that retries happened without wrapping the root cause in a separate error type (T1).
- **E8.** In Node.js, an unhandled promise rejection can terminate the process; in Python, `asyncio` logs errors for unretrieved task/future exceptions. Callers who rely on `close()` rather than awaiting individual tickets should encounter neither.

## T. Retries, timeouts, and canceling

- **T1.** Surfacing the last attempt's error directly lets callers handle a timeout as a timeout regardless of how many retries preceded it. A wrapper error for "retries exhausted" would hide the real cause behind boilerplate unwrapping.
- **T2a.** Ensure, reconfigure, delete, revoke, and `set_default_location()` each converge to a target state, so repeating them cannot produce an extra side effect.
- **T2d.** Access token IDs and network policy slugs are unique per account, so retrying `issue_access_token()` or `create_network_policy()` cannot create a duplicate resource. However, if the first attempt succeeded and its response was lost, a retry fails with a definite `409`, falsely implying nothing happened (and for access tokens, permanently losing the one-time secret). Neither has an indefinite wrapper or request token, so both retry only on definite errors.
- **T4.** Sending `s2-attempt` gives the service visibility into client retry rates without separate telemetry. Sending `1` on the first attempt distinguishes first tries from older clients that omit the header. Resetting the counter when session budget resets—and excluding planned handovers—keeps long-running healthy sessions at `1`. Counting retries consumed from the budget (rather than raw requests) handles handovers and request-per-batch transports uniformly without special cases.
- **T5a.** A heartbeat proves the read session's connection is alive. A session idling at the tail receives only heartbeats; without resetting the budget on heartbeats, isolated transient failures hours apart would accumulate and kill the session.
- **T5b.** Long-lived stream consumers often want to recover from transient failures indefinitely. The policy is named `unbounded` rather than `indefinite` to avoid colliding with the spec's meaning of "indefinite" (may have had side effects).
- **T6.** A planned handover is not an error, so it consumes no retry budget and applies no backoff. Append handovers follow `s2s.md`, waiting for the server to acknowledge all sent batches before switching requests—and switching as soon as those acks arrive rather than waiting unboundedly for a trailing EOF. Counting a handover as a retry when the previous request never made progress prevents tight retry loops against a repeatedly draining server. Moving to a different connection avoids landing back on the retiring server; retiring the connection globally across the client ensures no other session or call opens new requests on it either. `hot_server` (`502`) also signals that the server is shedding load and closing the connection, so retiring the connection avoids racing `GOAWAY` back onto the same overloaded server, while still consuming retry budget and backing off so fleet-wide overload does not trigger zero-backoff reconnect storms.
- **T7c.** An ack is the server's response to a batch, so ack timeout and `request_timeout` represent the same concept ("how long the server takes to answer") and share one setting, matching Python's existing design. Only the oldest unacked batch is timed because the server throttles rate-limited sessions by reading slowly; timing every queued batch from write time would falsely time out a throttled session. Starting the timer no earlier than the batch's last byte is sent prevents large batches on slow links from timing out while still uploading.
- **T7d.** Pausing the heartbeat timer while the caller has not consumed buffered records prevents slow consumers—where transport flow control legitimately pauses the server—from triggering false heartbeat timeouts. Go and Rust already behave this way.
- **T8.** A wait belongs to the caller, not the session: canceling a wait means the caller stopped waiting, not that the session should be aborted. Session work and outcomes therefore continue unaffected.
- **T9.** Previously, SDKs handled premature stream endings ad hoc and inconsistently: Go and Python treated truncated frames at EOF as clean endings, and Python treated an append response ending with unacked batches as success. A single decision table ensures uniform classification. Truncated streams are retryable `ConnectionLostError`s because the response never completed; only a complete, undecodable message is a non-retryable `ProtocolError`, since retrying would decode it the same way. Requiring all sent batches on an advised append attempt to be acked before treating a clean end as a T6a handover prevents a premature EOF from silently resending an unacked batch without retry accounting or indefinite-append tracking. Treating retryable terminal errors on an idle append session (nothing unacked) like an idle break keeps transient server shutdowns from failing idle sessions under `max_attempts = 1` or triggering eager idle reconnects (A3).
- **T10.** An ended attempt can still emit stale events (late acks, reset errors, expired timers). Ad hoc guards across the SDKs repeatedly missed edge cases. Defining a clean boundary—drain events received before ending, ignore everything after—prevents races without losing acks.

## A. Appending

- **A2.** Every limit mirrors a server limit, except a `Producer`'s `max_batch_bytes` (which no larger record could fit into). Validating upfront returns `ValidationError` before network I/O and ensures a single bad record never kills an open session.
- **A3.** Opening an append session sends no request because there is nothing to send yet. Connecting lazily avoids auto-creating empty streams when `create_stream_on_append` is enabled, avoids holding idle server streams or burning retry budget on transient blips before the first `submit()`, and behaves identically across `s2s` and `fetch` transports (C5). An idle response that ends cleanly or breaks later costs no retry budget (T9), and errors surface uniformly through tickets and `close()`.
- **A3b.** Having `Producer` create and own its `AppendSession` avoids shared ownership bugs where a caller closes the underlying session out from under the `Producer`.
- **A5.** Even with a zero `linger`, runtime timers yield until the next tick (e.g., Tokio or Node timers), allowing records submitted together in a tight burst to coalesce into one batch.
- **A5a.** Because accepted records count against `max_unacked_bytes` while lingering (A4a) and capacity is FIFO, a `Producer` with `max_unacked_bytes = 1 MiB` that accepts a 600 KiB record and then receives another 600 KiB `submit()` would otherwise stall for the full `linger` (or deadlock with a very large `linger`) with nothing in flight. Restricting this flush to when no other batch is unacked still prevents that stall while avoiding tiny-batch fragmentation under steady backpressure (where an in-flight ack will free capacity on its own, preserving batch sizes under the 200 batches/s limit). Since `max_unacked_bytes ≥ 1 MiB ≥ max_batch_bytes`, when nothing else is unacked the waiting record could not fit in the partial batch anyway.
- **A5b.** All four SDKs already had standalone batchers under different names and APIs (Go's `Batcher`, TypeScript's `BatchTransform`, Rust's `AppendRecordBatches`, and Python's `append_record_batches()` / `append_inputs()`) for callers driving `append()` or `AppendSession` directly. Attaching `fencing_token` and `match_seq_num` lets emitted batches pass directly to `append()` or `submit()`. Pausing input reads while a completed batch awaits consumption provides backpressure, bounds memory, and ensures errors or consumer stops can drop at most the current partial batch. Failing immediately on input error matches stream conventions (and TypeScript's `TransformStream` discards queued chunks on error anyway). Go takes a channel so it can `select` on incoming records and the linger timer together, and returns a pull iterator—avoiding the deadlock-prone push API that required a dedicated draining goroutine.
- **A6.** A single outcome table ensures all four SDKs report identical outcomes for every batch on any failure mode (verified by the example after A9). `Producer` tickets return `RecordAck` (with the record's own `seq_num` plus its batch's `AppendAck`) because callers submitting individual records want that record's sequence number. Renamed from `IndexedAppendAck` because it carries `seq_num` rather than an index and pairs cleanly with `AppendAck`. Records still being batched when a session closes were never sent, so they receive `SessionClosedError` like any unsent batch.
- **A6c.** Reporting `SessionClosedError` for batches queued behind a definite rejection is valid only because the server guarantees no subsequent batch in the session becomes durable. TypeScript's `fetch` transport has no server-side session, so it enforces this locally by keeping at most one batch in flight at a time and sending nothing after a definite rejection.
- **A7.** Linearizing coverage and the partial-batch cut at a single point in acceptance order prevents two races with concurrent `submit()` calls: cutting the batch before snapshotting accepted records can leave a covered record lingering in a new partial batch, while snapshotting before cutting can co-batch an uncovered later record into the covered batch so a server error on the later record fails `flush()`. For split-acceptance APIs (Rust's `reserve()` + permit `submit()`, Go's `Submit()` + `Wait()`), only completed acceptances are covered so `flush()` never blocks behind an unsubmitted reservation.
- **A8a.** `close()` flushes any partial batch immediately rather than waiting out `linger`, since no more records can be accepted. Waiting strictly for outcomes (and nothing else) avoids hangs on unrelated background work.
- **A8c.** Aborting an idle append session loses nothing, so it closes cleanly. Aborting a read session always fails iteration (R9d) because ending cleanly would be indistinguishable from hitting a stop condition.

## R. Reading

- **R1.** Read start is optional, matching the API (which defaults to the tail); the same reasoning as R2 applies.
- **R2.** Read stop options and their defaults belong to the API. Leaving omitted options unset ensures reads behave identically across every SDK and raw HTTP calls. The specification avoids restating API option semantics or every `416` condition so it cannot drift from API docs; the [Server guarantees](spec.md#server-guarantees) table lists only the cases SDK rules depend on.
- **R3.** Returning the server's batch unchanged ensures the next unary read always starts at one past the last returned record, or at the same position if the batch was empty.
- **R5.** Starting the first request immediately on open begins prefetching right away, while surfacing all errors through iteration gives callers one place to handle errors.
- **R6a.** A batch view should deliver only actionable data; exposing heartbeats as empty batches would leak transport details.
- **R6b.** Byte-based read-ahead already lives in transport flow control, tuned per transport. Decoding at most one batch ahead keeps decoding off the caller's critical path without duplicating transport buffering with an unpredictable multi-megabyte queue of decoded batches.
- **R7.** Tracking `next_seq_num` by delivered records rather than fetched records ensures checkpoints never skip records the caller has not processed. Advancing `next_seq_num` on heartbeats handles streams where early records were trimmed, allowing the session to catch up. `last_observed_tail` and `is_caught_up` reflect only what the server has reported; `is_caught_up` requires an open request because a broken connection may have missed newer writes. Treating a stop-condition response as open until iteration finishes avoids race conditions between draining the final batch and seeing EOF. Once iteration ends, the session is no longer observing the stream, so `is_caught_up` becomes false.
- **R9b.** If a reader exits its loop and closes the session, it makes no further reads. If another task closes the session while the reader is waiting, finishing cleanly would falsely look like a stop condition, so waiting reads fail with `SessionClosedError`. Basing this on state rather than caller identity works in Go, where goroutine identity is unavailable. TypeScript follows the Web Streams standard (reads after `cancel()` resolve as done) and uses `AbortSignal` to fail a reader with an error.
- **R11b.** Omitting `clamp` once the start has been resolved to an absolute `seq_num` ensures that if a stream is recreated at a lower tail, a reconnect fails with `416` rather than silently clamping backward.
- **R11c.** On a read session, `wait` bounds idle time between records, so the clock restarts when a record is fetched. Heartbeats only indicate idleness—restarting `wait` on heartbeats would keep a bounded session alive forever. Rounding remaining `wait` up to whole seconds avoids ending the session early, since the API accepts integer seconds. Because the server only sees the reduced `wait` query parameter sent on a resumed request, a record arriving on that request resets the server's timer only to that reduced value; continuing on a fresh request when the full `wait` has not elapsed restores the configured inter-record wait (and if `until` actually triggered the stop, the follow-up request ends cleanly immediately with zero records). Closing cleanly once remaining `count` or `bytes` hits `0` avoids sending a redundant `?count=0`/`?bytes=0` reconnect.
- **R11d.** With `wait` of 0 (explicitly, after R11c elapses, or by API default when `count`, `bytes`, or `until` is set), the API returns `416` at the tail. If a bounded session reconnects with no `wait` remaining and receives `416`, it has reached its stop condition rather than encountered an error. Restricting this to zero remaining `wait` ensures a `416` received while `wait > 0` (for example, after a stream is deleted and recreated) still surfaces as an error. When that stop-condition `416` includes `tail`, treating it like a final heartbeat ensures `next_seq_num` advances past any trimmed gap and pending `caught_up()` callers receive the tail rather than `SessionClosedError`.

## M. Managing basins, streams, access tokens, and network policies

- **M2.** Ensure sets the resource's full configuration (matching server semantics) so repeated calls converge to the same state regardless of prior config; reconfigure is the partial-update operation. `created`, `updated`, and `noop` match the server's `s2-provision-result` values (already used by Go and TypeScript). When the header is missing (for example, stripped by a proxy), interpreting `201` as `created` and other 2xx responses as `updated` avoids understating what may have changed. Because the header reflects only the final attempt, a retried call that created a resource may report `updated` or `noop`.
- **M4.** Delete ensures a resource does not exist, so "already gone" is success. `ignore_not_found` was removed because after a retry, the SDK cannot tell whether a `404` means the resource never existed or was deleted by an earlier attempt—making the error unreliable. Only the resource's own not-found code counts as success: a `404` for a missing parent basin when deleting a stream, an uncoded proxy `404`, or a `409 network_policy_in_use` indicates a real failure. Delete returns no boolean for whether the resource existed for the same retry-ambiguity reason; callers who need that check can query first.
- **M6, M7, M8.** Returning server pages untouched preserves exact page lengths and `has_more` semantics. `list_all_*` is the high-level helper and filters out deleting resources by default, matching all four SDKs today. Advancing `start_after` from the unfiltered server page ensures a page full of deleting resources does not stall or truncate pagination.

## F. Forward compatibility

- **F2.** The API evolves both string enums and externally tagged `oneOf` unions (such as adding `record` to `Metric`, or new cloud providers to `PrivateNet`). Requiring unknown variants to be exposed by wire tag—as Rust and Python already do—prevents closed-union compile-time exhaustion traps in TypeScript and silent all-`nil` structs in Go.

## L. Logging

- **L2.** A library cannot decide which failures warrant application-level warnings or alerts. Returning errors to the caller while also logging them at warn/error duplicates error reporting.
- **L3.** Tokens, encryption keys, and record bodies should travel only to configured endpoints and never leak into application logs—including error messages, which applications routinely log.

## Settings and constants

- **`linger`.** The 5 ms default aligns with the server's limit of 200 batches per second per stream/connection, keeping partial-batch producers within that rate automatically.
- **`max_attempts`.** Because it counts the initial attempt, the minimum is 1.

## Languages

- **Numbers and byte inputs.** TypeScript's `2⁵³ − 1` cap is the only place a language narrows the API's integer range (see D4). Mutable byte inputs must be copied on acceptance so C10 holds even if the caller reuses or modifies the buffer.
- **TypeScript stream adapters.** Breaking out of a `for await` loop over `readable` stops observing acks rather than requesting data loss, so canceling `readable` closes gracefully (matching `Producer`). Aborting `writable` remains the abort trigger. Queued stream writes represent already-issued submissions, so `close()` and `flush()` wait for them just like returned `submit()` calls.
- **TypeScript over `fetch`.** The host runtime controls `fetch`'s connection pool and redirect handling, so connection-level and redirect rules apply as far as the runtime permits.
- **Python `async with`.** Exiting on an ordinary `Exception` closes gracefully so an application bug inside the `with` block does not discard already-accepted appends; the exception propagates once those appends settle. `CancelledError`, `KeyboardInterrupt`, and `GeneratorExit` abort because execution is being terminated.

## Server guarantees

Several rules are sound only under specific server invariants. Collecting those invariants in one table with their authoritative sources makes it easy to audit SDK impact whenever server behavior changes.

## Conformance

- **Vectors.** All four SDKs previously hit and fixed the same edge cases independently (trailing slashes on endpoints, `NaN` timestamps, bare IPv6 hosts, zero-length frames). Storing shared test vectors in `s2-specs` lets every SDK test them once via its existing submodule, automatically picking up new cases whenever the pin advances.
